# Правила проекта gigaschool-rag

Сквозной RAG-проект курса «LLM-инженер»: пять контрольных точек (КТ) и финальный отчёт.
План и чек-листы — `PLAN.md`, ТЗ — `docs/` (не публикуется).

## Структура

```
src/gigarag/          общая библиотека: весь переиспользуемый код и все вычисления
  patterns.py         ВСЕ регулярные выражения проекта
  sources/            источники корпуса: чистый парсинг «сырой файл → Document»
scripts/              тонкие CLI всех КТ; settings.py — общие пути и параметры
notebooks/            ноутбуки КТ: kt<N>_<тема>.py (jupytext) + .ipynb
reports/              отчёты КТ: kt<N>.md — решения, таблицы, выводы
gold/                 золотой набор и решения ревью (в git)
data/                 сырьё, корпус, кэши (вне git)
tests/                pytest на функции библиотеки
```

- КТ не получает своей папки: она добавляет ноутбук `notebooks/kt<N>_*`, отчёт `reports/kt<N>.md`
  и при необходимости скрипты. Каждая КТ — в своей ветке `kt<N>` и своём PR.
- Код, нужный больше чем в одном месте, живёт в `src/gigarag`, а не копируется между КТ.
- Скрипты (`scripts/`) — тонкие CLI: читают конфиг (`settings.py`), вызывают библиотеку, печатают итог.
- Ноутбуки — только оркестрация, таблицы, графики и выводы. Никаких формул, регулярок и парсинга внутри ячеек.
  Исходник ноутбука — `.py` в формате jupytext percent; `.ipynb` хранится исполненным, с выводами.

## Принципы кода

**SOLID**
- *SRP*: модуль и функция отвечают за одно. Скачивание, парсинг, отбор, запись — разные функции.
- *OCP*: новый источник данных — новый класс с методом `documents()`, сборщик корпуса не меняется.
- *LSP/ISP*: протоколы узкие (`DocumentSource` — одно поле и один метод).
- *DIP*: высокоуровневый код зависит от абстракций: сборщик — от `DocumentSource`, подсчёт классов токенов —
  от функции `offsets`, а не от конкретного токенизатора.

**GRASP**
- *Information Expert*: поведение — у того, у кого данные (`Document.with_meta`, `RetryPolicy.backoff`, `Names.hero`).
- *Controller*: `main()` скрипта только связывает шаги.
- *Low Coupling / High Cohesion*: модули библиотеки не знают про ноутбуки и КТ; связанное лежит вместе.
- *Pure Fabrication*: служебные классы (`CacheStore`, `PoliteFetcher`) выделены, а не размазаны по коду.

**Функциональный стиль — по возможности**
- Чистые функции без побочных эффектов; ввод-вывод — на краях (в источниках и скриптах).
- Неизменяемые данные: `@dataclass(frozen=True)`, `frozenset`, копии через `dataclasses.replace`.
  Входные аргументы не мутируются.
- Генераторы, comprehension, `itertools` вместо циклов с накоплением; функции высшего порядка
  (`build_any_matcher`, `load_or_compute`) вместо копипасты.
- Случайность — только через явно переданный генератор (`random.Random(seed)`), никогда глобальная.

**Регулярные выражения**
- Все регулярки — в `gigarag/patterns.py`, скомпилированы на уровне модуля и приватны (`_NAME`).
- Снаружи доступны только функции с семантическими именами: `strip_tags`, `url_spans`, `has_ads_marker`,
  `patch_from_slug`. По имени должно быть понятно, *что* ищется, без чтения шаблона.
- Если библиотеке нужен токенизатор, передаётся функция (`tokenizer=patterns.topic_words`), а не строка шаблона.

**Формулы и вычисления**
- Любая нетривиальная формула — отдельная чистая функция с семантическим именем и docstring с формулой:
  `jaccard`, `lsh_candidate_probability`, `class_tfidf`, `offtopic_quota`, `latin_letter_share`.
- Магические числа — именованные константы (`SHORT, LONG = 50, 2000`, `GENERAL_ITEM_ID = -1`).

**Общее**
- Аннотации типов везде, где они не очевидны; docstring — на русском, зачем и что возвращает.
- Комментарии объясняют *почему*, а не *что*.
- Имена — по смыслу предметной области, без сокращений (`article_id`, не `aid`).
- Без мёртвого кода и задела «на будущее».

## Воспроизводимость

- Сборка данных детерминирована: файлы обходятся в отсортированном порядке, выборки — из популяции,
  упорядоченной по ключу, с seed. Не использовать `hash()` для идентификаторов — только `hashlib`.
- `doc_id` уникальны и стабильны — на них ссылаются gold-набор и кэши; уникальность проверяется при сборке.
- После изменения кода сборки sha256 корпуса должен остаться прежним (или изменение объясняется в отчёте КТ).
- Кэши — через `CacheStore`: ключ включает sha256 данных, параметры и `code_fingerprint` модулей,
  от которых зависит результат. Кэш, принятый «по факту существования файла», запрещён.
- Модели Hugging Face — только с `revision=<commit sha>`; ревизия входит в ключ кэша и в отчёт КТ.
- Многопоточные алгоритмы с плавающей точкой, дающие разный результат от запуска к запуску (KMeans),
  запускаются в однопоточном режиме (`gigarag.clustering.deterministic_kmeans`).
- Устройство — `cuda`, если есть, иначе `cpu` (`gigarag.embeddings.pick_device`); код не требует GPU.

## Метрики и выводы

- Единицы измерения согласованы: доли «в токенах» считаются тем же токенизатором, что и длины.
- Вероятностные методы (LSH) — только для кандидатов; итог проверяется точным расчётом.
  Если полноту нельзя гарантировать, это явно называется оценкой снизу и обосновывается.
- Цифры в отчёте и выводах ноутбука берутся из исполненного ноутбука, а не прикидываются.

## Проверки перед коммитом

```bash
uv run ruff check src tests scripts notebooks
uv run pytest
```

Ноутбук КТ перевыполняется целиком после изменений, влияющих на результаты.

## Git и документация

- Коммиты — короткий заголовок `type(scope): описание` на русском, без строк о соавторстве.
- Сырые данные, корпуса и кэши (`data/`) в git не попадают: это контент третьих сторон.
- Каждое решение по данным и методике записывается в отчёт своей КТ (`reports/kt<N>.md`); отмечаются пункты в `PLAN.md`.
