# КТ 4 — Трансформация запросов, реранкинг и оценка качества ретрива

Текст задания из ТЗ курса «LLM-инженер» (GigaSchool). Дедлайн: 21 октября.

## Baseline

Берём конфигурацию из КТ 3, прогоняем её (или вспоминаем старые метрики, лежащие в сервисе для логов
экспериментов) — это будет baseline.

## Трансформация запросов — один метод на выбор

Выбрать один метод из списка и реализовать его полноценно, а не поверхностно:

- **HyDE** — сгенерировать гипотетический документ-ответ на запрос и искать по его эмбеддингу вместо эмбеддинга
  самого вопроса.
- **Multi-query expansion** — сгенерировать 3–5 перефразировок запроса, прогнать каждую через ретривер,
  объединить результаты через RRF.
- **Step-back prompting** — переформулировать конкретный вопрос в более общий, искать по обоим и объединить.

Для выбранного метода обязательно:

- Обосновать выбор — почему именно этот метод подходит для данного корпуса и типов вопросов.
- Замерить прирост Recall@5 и NDCG@5 относительно baseline.
- Разбить результаты по типам вопросов из gold_dataset — для каких типов метод помогает, для каких нейтрален
  или вредит.
- Зафиксировать добавленную latency и стоимость в токенах на запрос.

Вопрос: оправдывает ли прирост качества дополнительные затраты и при каком сценарии использования этот метод
стоит включать в пайплайн?

## Реранкинг — оба подхода обязательны

### Cross-encoder reranking

Выбрать модель из `cross-encoder/*` на Hugging Face, подходящую для языка корпуса. Выбор обосновать — не брать
первую попавшуюся.

Обязательный эксперимент:

- Размер candidate pool перед реранкингом: топ-20 / топ-50 / топ-100 от первичного ретривера — как меняется
  Recall@k и как меняется latency при каждом значении.
- Порог отсечения по score: найти оптимальный порог на gold_dataset, показать precision/recall trade-off.
- Два сценария применения: реранкинг поверх только dense vs поверх hybrid — сравнить прирост.

### LLM-as-reranker

Реализовать реранкинг через LLM: подать запрос + N чанков, получить отсортированный список.

Предлагаемый пул экспериментов:

- [Опционально] Два формата промпта: pointwise (оценить каждый чанк отдельно по шкале 0–2) vs listwise
  (отсортировать все чанки сразу) — сравнить качество, стабильность и стоимость.
- Размер candidate pool: топ-5 / топ-10 / топ-20 — при каком N качество перестаёт расти, а latency и стоимость
  продолжают.
- Проверка детерминированности: прогнать 20 одинаковых пар дважды при температуре 0, посчитать agreement rate.
  Если ниже 90% — доработать промпт и задокументировать итерации.

## Измерение latency — обязательно наравне с качеством

Для каждой конфигурации замерить полный профиль по этапам:

| Этап | Что измерять |
|---|---|
| Трансформация запроса | Время генерации + стоимость токенов |
| Эмбеддинг запроса | Время энкодинга |
| Поиск в индексе | Время retrieval |
| Cross-encoder reranking | Время scoring для N кандидатов |
| LLM-as-reranker | Время + стоимость токенов |
| Итого | End-to-end latency на один запрос |

Метрики: медиана, p95 по 100 запросам. Явно указать, какой этап является bottleneck в каждой конфигурации.

Желательный вывод — график: ось X — медианная latency, ось Y — Recall@5. Нанести на него все конфигурации.
Наглядная демонстрация, какое улучшение качества «стоит» своей задержки, а какое нет. Финальный выбор
конфигурации для КТ 5 обосновать через этот график, а не просто через лучшие метрики качества.
