# КТ 2 — Предобработка, чанкинг и метаданные

Текст задания из ТЗ курса «LLM-инженер» (GigaSchool). Дедлайн: 7 октября.

Отправная точка — датасет для ретрива без чистки.

Прежде чем что-либо чистить, нужно запустить простейший retriever (например, TF-IDF или BM25 по документам
из КТ 1, после разбиения обычным token-чанкером с размером 512 в качестве baseline) и замерить Hit@k, Recall@k
на gold_dataset. Это число станет точкой отсчёта для всего КТ 2 — каждое последующее решение оценивается
относительно него.

## Предобработка

Задача — не «почистить как можно лучше», а задокументировать каждое решение и его эффект.

Обязательные шаги с измерением до/после каждого:

- Удаление HTML/Markdown-разметки, скриптов, навигации.
- Нормализация пробелов, переносов строк, Unicode.
- Обработка эмодзи и спецсимволов (это не обязательно полное удаление; иногда нужно признать, что они,
  наоборот, улучшают работу системы).
- Дедупликация — exact и near-duplicate (MinHash или аналог); зафиксировать, сколько процентов корпуса отсеялось.

Что должно быть в отчёте: таблица с метриками корпуса до и после каждого шага — размер, доля шумовых токенов,
Hit@k, Recall@k на gold_dataset. Если шаг не улучшил метрику — это тоже результат, его нужно объяснить.

## Чанкинг

Обязательный минимум — попробовать все основные стратегии.

Из Chonkie протестировать не менее четырёх чанкеров, охватывающих разные принципы:

| Чанкер | Принцип | На что обратить внимание |
|---|---|---|
| TokenChunker | Фиксированный размер по токенам | Baseline для сравнения |
| SentenceChunker | По границам предложений | Поведение на коротких постах без знаков препинания |
| SemanticChunker | По семантическому сдвигу | Стоимость вычислений vs. прирост качества |
| SDPMChunker или NeuralChunker | Более сложные модели | Сравнить с семантическим |

Для каждого чанкера зафиксировать: среднее и медианное количество токенов в чанке, стандартное отклонение,
долю чанков короче 50 и длиннее 500 токенов, метрики на gold_dataset.

Один подход разобрать детально. Выбрать семантический чанкинг как наиболее нетривиальный и провести
полноценный ablation:

- Варьировать порог семантического сдвига и обосновать сетку значений (например, пороги по cosine similarity)
  и показать, как меняется средний размер чанка и метрики ретрива.
- Сравнить два разных эмбеддера для определения границ чанков — показать, что выбор модели влияет на разбиение.
- Визуализировать несколько примеров: один и тот же текст, разбитый при разных порогах — это лучший способ
  объяснить, что происходит внутри.

## ParentDocumentRetriever

Отдельный эксперимент с более сложным чанкером:

- Реализовать схему: крупный родительский чанк + мелкий дочерний для индексирования; попробовать с моделью
  эмбеддингов BGE-M3 из семинара.
- Протестировать минимум три комбинации размеров parent/child.
- Ответить на вопрос: при каких типах вопросов из gold_dataset (фактические / составные / абстрактные) этот
  подход выигрывает у лучшего простого чанкера и почему.

## Метаданные

Задача в два этапа: сначала извлечь, потом доказать, что они полезны.

Извлечение — выбрать метаданные, специфичные для своего корпуса, но обязательно покрыть:

- Структурные: дата публикации, источник, длина документа, позиция чанка в документе.
- Контентные: топ-5 ключевых слов (KeyBERT или TF-IDF), язык, тип контента (если смешанный корпус).
- Качественные: оценочный «шумовой score» чанка — доля неалфавитных токенов.

Применение — обязательно протестировать хотя бы два сценария использования и замерить эффект на метриках:

- Фильтрация при ретриве по метаданным (например, только свежие документы или только конкретный источник) —
  показать precision до и после фильтрации.
- Добавление метаданных в текст чанка перед индексированием (prepend) — влияет ли это на качество поиска.

## LLM-обработка чанков

- Суммаризация — заменить чанк его резюме; замерить, как меняются метрики ретрива. Гипотеза об ожидаемом
  результате: хуже на фактических вопросах, лучше на абстрактных.
- Генерация гипотетических вопросов (HyDE-style) — для каждого чанка сгенерировать 2–3 вопроса, на которые
  он отвечает, и индексировать вопросы вместо текста.

Для обоих подходов: зафиксировать стоимость в токенах, время на обработку, прирост/падение метрик. Вывод должен
отвечать на вопрос — оправдывает ли прирост качества затраты.

## Итоговая сравнительная таблица

К концу КТ 2 должна существовать таблица, где каждая строка — это конфигурация (предобработка + чанкер +
метаданные + LLM-обработка да/нет), а столбцы — метрики ретрива, средний размер чанка, время индексирования.

## Дизайн экспериментов

Рекомендуется использовать последовательный дизайн экспериментов:

- На раннем этапе сравнивайте методы при фиксированных разумных настройках, чтобы отобрать один-два наиболее
  перспективных кандидата.
- Гиперпараметры настраивайте только для отобранных кандидатов и только на validation split.
- Меняйте за один эксперимент один основной фактор; остальные параметры фиксируйте и документируйте.
- Для дорогих операций — LLM-генерации вопросов, извлечения ключевых слов, семантического чанкинга, эмбеддингов
  и построения индекса — используйте кэширование промежуточных результатов и не пересчитывайте
  неизменившиеся артефакты.

Допускается сокращать число конфигураций или размер промежуточной выборки для exploratory-экспериментов,
если выбор сокращения обоснован.
