## Конфигурации контекста

- **baseline retrieval** — топ-5 baseline КТ 3: BGE-M3 + BM25 (k1 = 0,3, b = 1,0), взвешенная сумма alpha = 0,6,
  фильтр по патчу из запроса.
- **best retrieval** — топ-5 лучшей конфигурации КТ 4: тот же поиск + LLM-реранкер listwise (промпт v2 «оценки 0–2
  всей пачке»), пул 20.

У половины вопросов (25 из 50) набор топ-5 в двух конфигурациях одинаковый. Чанки — с префиксом метаданных
(заголовок, тип, патч, дата), как в КТ 3–4.

## Генерация

**Модель** — `deepseek-flash`, t = 0, seed 42, `thinking: disabled`; та же, что у реранкера КТ 4. О фиксации
версии — в разделе «Воспроизводимость модели». **Промпт** — `gigarag.generation.SYSTEM`, версия 1, без изменений
на всё КТ 5:
- отвечать только по фрагментам, не по собственным знаниям об игре;
- если ответа во фрагментах нет — ровно «Не знаю: в найденных материалах нет ответа.» (так же — если фрагменты
  про другую сущность или другой патч);
- если ответ есть на часть вопроса — ответить на неё и сказать, какой части нет;
- использовать все фрагменты, относящиеся к вопросу, и ставить номер фрагмента после каждого утверждения.

Отказ распознаётся без LLM — по началу ответа (`patterns.is_abstention`). Стоимость — 1 429 входных и 113 выходных
токенов на ответ, $0,56 на 1000 ответов; медиана ответа API — 1,18 с.

**Отказы по типам вопросов**, %:

| | factual | composite | abstract | negative |
|---|---|---|---|---|
| baseline retrieval | 6,7 | 0,0 | 50,0 | **100** |
| best retrieval | 0,0 | 6,7 | 40,0 | **100** |

Проверка на негативных пройдена. Ложные отказы почти все на абстрактных вопросах: модель не находит ответа
на «как менялось отношение сообщества к …» в пяти отдельных постах.

## LLM-судья

**Три критерия — три отдельных запроса** (`gigarag.judge`), шкала 1–5 с описанием каждого балла:
- **faithfulness** — подтверждается ли каждое утверждение ответа фрагментами;
- **answer relevance** — отвечает ли ответ на вопрос;
- **context utilization** — использует ли ответ всю относящуюся к вопросу информацию из фрагментов.

Судья видит вопрос, фрагменты и ответ, но не эталон gold: критерии — про связь ответа с контекстом и вопросом.
**Отказ** оценивается по тому, есть ли ответ в контексте: достоверность — 5; релевантность и использование — 5,
если ответа во фрагментах нет, и 1, если есть.

Шкалы (`judge.SCALES`) одни и те же во всех версиях промпта и на странице ручной разметки — человек и судья
оценивают по одной шкале. Модель судьи та же — `deepseek-flash` без рассуждения, t = 0.

2. **v1, faithfulness, q08 — 5 / 4.** Два фрагмента противоречат друг другу (что даёт Yasha and Kaya), ответ

4. **v1, relevance, q30 — 5 / 4.** Вторая часть вопроса «закрыта» общими цитатами комментариев не по теме.

5. **v1, utilization, q04 и q37 — 5 / 4.** Что считать «относящимся к вопросу»: только урон, о котором спрашивают,

6. **v2, relevance, q35 — 1 / 5; utilization, q36 — 5 / 1.** Свободный разбор каждый раз уводит рассуждение в другую

7. **v3, faithfulness — неверное число как «неточность».** Найдено не по расхождению прогонов, а контрольной
   выборкой (ниже): v3 ставила 4 ответу, где значение отличается от фрагмента. v4 выделяет противоречие в отдельное
   поле с правилом «другое число, патч или название — противоречие, не неточность»; тексты релевантности
   и использования — те же, что в v3.

**Что осталось в v4** — 4 расхождения из 90, все в релевантности и использовании: случаи 1/5 (q39, q48), где модель
по-разному решает, есть ли ответ во фрагментах абстрактного или негативного вопроса, и два пограничных 3/4.

## Проверка судьи достоверности на искажённых ответах

Человек поставил достоверность 5 всем ответам и dev, и holdout. На такой выборке судья, всегда ставящий 5,
неотличим от хорошего, и kappa с человеком по этому критерию ничего не проверяет. **Контрольная выборка**
(`gigarag.perturbation`): ответы, которые человек признал достоверными (≥ 4, не отказы), и две их копии:
- **число заменено** — одно значение ответа заменено другим, которого нет ни в одном фрагменте;
- **добавлен факт** — к ответу дописано правдоподобное утверждение со ссылкой [1] и числом, которого нет во фрагментах.

Метка — по построению: исходный ответ достоверен, искажённый — нет (по шкале — не выше 3). «Поймал» — балл ≤ 3.

**Контроль dev** (23 исходных, 21 с заменой числа — в двух ответах чисел нет, 23 с добавленным фактом):

| Версия | Ложная тревога на исходных | Поймано: число заменено | Поймано: добавлен факт | κ |
|---|---|---|---|---|
| v1 | 0% | 29% | 91% | 0,52 |
| v2 | 0% | 29% | 96% | 0,55 |
| v3 | 0% | 33% | 96% | 0,57 |
| **v4** | 4% | **95%** | **100%** | **0,93** |

v1–v3 ловят выдуманный факт, но заменённое число считают «неточностью пересказа» и ставят 4. Ложная тревога v4 —
q08: исходному ответу v4 поставила 1. В ответе действительно есть ошибка, которую пропустили и человек, и v1–v3:
«во фрагменте [2] для Yasha and Kaya … +25% к сопротивлению замедлениям» — этого нет ни в [2], ни для Yasha
and Kaya, это правка Sange and Yasha из [4]. Но главный ответ (стоимость) верный, и по шкале здесь 3, а не 1:
v4 нашла проблему, но завысила её тяжесть.

**Контроль holdout** (v4 заморожена; 11 исходных, 11 + 11 искажённых): ложных тревог — 0, поймано 11 из 11
и 11 из 11, κ = 1,0.

### Почему лучший поиск не поднял релевантность

На фактических вопросах best retrieval лучше (релевантность 4,18 → 4,55). На абстрактных — хуже (3,57 → 2,14),
и это перевешивает. Разбор семи абстрактных вопросов validation:
- **q40:** с baseline контекст пустой, судья видит «ответа нет» — отказ честный, релевантность 5. С best контекст
  частично полезный — тот же отказ получает 1.
- **q37:** с baseline — честный отказ, 5. С best модель ответила, но про другое (общие жалобы на патчи вместо багов
  с аспектами), 1.
- **q31:** с baseline ответ закрыл все части вопроса, 5. С best — только направление изменений карты, без влияния
  на объекты, 3.

Использование контекста на абстрактных при этом выросло (2,71 → 3,29). Лучший поиск приносит больше относящегося
к вопросу материала, но генератор не собирает из разрозненных постов ответ на «как менялось отношение сообщества».
Судья без эталона оценивает ответ относительно контекста, поэтому честный отказ при пустом контексте выглядит
лучше, чем слабый ответ при частично полезном.

## Воспроизводимость модели

У DeepSeek нет неизменяемого ID версии: `/models` отдаёт алиас `deepseek-flash` (DeepSeek-V4.1-Flash), который
обновляется на сервере. Поэтому:
- **Идентичность каждого ответа записывается.** `ChatResponse` хранит `model`, `system_fingerprint` и id ответа API.
  Поле появилось после генерации ответов и первых версий судьи. У 100 ответов генерации и 200 вердиктов судьи
  (релевантность, использование — общие с v3) fingerprint не записан. У 100 вердиктов достоверности v4 и всех
  вызовов контроля он записан: `bc19ba97cbe016479903222bb1578db6`.
- **Результаты лежат в git как артефакт эксперимента.** Ответы генератора с номерами чанков контекста —
  `gold/kt5_answers.jsonl`, все вердикты финального судьи — `gold/kt5_verdicts.jsonl`, разметка —
  `gold/kt5_human_labels*.json`. Выводы КТ 5 проверяются по этим файлам без вызовов API. Повторный запуск после
  обновления модели сравнивается с ними построчно.
- **Кэш LLM** (`data/llm_cache/`) по-прежнему вне git: в запросах — тексты корпуса.

## Вывод для финального отчёта

- **На фактических и составных вопросах система работает:** достоверность ≈ 5, релевантность 3,8–4,6.
  Лучший поиск даёт +0,37 релевантности на фактических.
- **Абстрактные вопросы не решены** ни поиском, ни генерацией: R@5 12,9% у baseline и 22,4% у best (КТ 4),
  ложные отказы 40–50%, релевантность 2,1–3,6. Следующий шаг — не реранкинг, а генерация с синтезом по многим
  фрагментам (map-reduce или агент с несколькими поисками).
- **Какую конфигурацию брать.** Для продукта — best retrieval: выше R@5, NDCG@5, использование контекста и меньше
  ложных отказов (12,5% против 15,0%). Цена — +1,2 с на запрос: поиск 1,27 с против 0,05 с у baseline, генерация
  у обеих ≈ 1,2 с.

## Решения по ходу КТ

- **Генератор и судья — `deepseek-flash` без рассуждения.** Выбрано из трёх вариантов (OpenAI gpt-4.1-mini + gpt-4.1,
  DeepSeek, смешанный). Риск — судья оценивает ответы своей же модели; holdout-kappa и контроль проверяют,
  насколько это мешает.
- **Судья без эталона gold** — критерии задания про связь ответа с контекстом, правильность по эталону мерили
  в КТ 1 (baseline без RAG).
- **Шкалы вынесены в общую константу** — промпт судьи меняется от версии к версии, шкала для человека и судьи нет.
- **Разметка dev — второй проход с нуля** после уточнения инструкции; первый проход сохранён и показан.
- **После ревью:**
  - добавлена контрольная выборка достоверности; по ней найдена слабость v3 и сделана v4;
  - подбор версии отделён от проверки: выбор на dev, итоговые цифры — на holdout, размеченном после заморозки;

## Воспроизведение

  в них тексты чанков корпуса). Оценки по id ответа — `gold/kt5_human_labels.json`, `gold/kt5_human_labels_pass1.json`,
  `gold/kt5_human_labels_holdout.json`.

## Код

| Модуль | Что делает |
|---|---|
| `gigarag.generation` | промпт генерации, контекст из пронумерованных фрагментов, запрос |
| `gigarag.judge` | шкалы трёх критериев, версии промпта судьи, разбор вердикта, оценка набора ответов |
| `gigarag.perturbation` | искажения ответа для контроля судьи достоверности: замена числа, выдуманный факт |
| `gigarag.annotation` | выборки и страница ручной разметки, хранение оценок |
| `gigarag.llm` | + идентичность модели в ответе: `model`, `system_fingerprint`, id |
| `gigarag.stats` | + weighted Cohen's kappa |
| `scripts/kt5_annotate.py` | локальный веб-сервер разметки: адрес на каждый ответ, сохранение каждой оценки |

Тесты — `tests/test_kt5_library.py`.
